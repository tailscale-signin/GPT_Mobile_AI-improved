# Research stability implementation — 24 October 2026

This records the production boundaries and acceptance coverage for the supplied `Research_Mode_Stability_Implementation_2026-10-23` design. It distinguishes implementation and regression fixtures from measurements requiring a phone or live provider. The branch-wide validation record is in [Stability implementation](Stability_Implementation_2026-10-24.md).

## Durable authorities and ordering

`ResearchTaskStore` writes a versioned atomic execution record containing the complete accepted task, requested policy payload, immutable source scope and target, participant/model selection, current attempt/generation, pending scheduling action and operational receipts. The `.task` file is a compatibility projection; reconciliation can rebuild it from the execution authority. Legacy tasks without a proven execution outcome import as interrupted and require an explicit action. AtomicFile backup recovery and deleted-chat tombstones prevent a missing projection or stale writer from silently replacing acceptance.

Acceptance precedes the running projection and resource wait. `ResearchDispatchLifecycle` carries the captured task/attempt fence through admission and physical dispatch. Stale generations, cancellation and changed authority fail before a provider invocation. Queueing records resource blockers and elapsed wait without consuming an invocation or creating provider response latency. There is no implicit 60-second admission timeout; an explicitly accepted deadline can still expire.

Room run ownership and the atomic Research record are different transactions. The implementation does **not** claim a distributed transaction between them. `ResearchStartupReconciler` repairs this boundary using current-attempt run receipts, ownership fences, readable captured evidence and matching delivery receipts. It runs after interruption/Combined reconciliation and before queued prompts resume. Unknown remote acceptance remains interrupted with `RECONCILE_REQUESTS`; startup never creates a replacement provider request.

The explicit recovery review can authorize a new attempt after showing the uncertain prior requests. Its captured attempt/generation is rechecked under the store lock, and the action ID is recorded atomically as `UNKNOWN_REMOTE_REQUESTS_REVIEWED_NEW_ATTEMPT_AUTHORIZED`. The previous attempt stays interrupted with its original dispatched IDs and receipts. Review acknowledgement does not claim that a remote service rejected, canceled or completed the old request.

An individual contributor cannot complete the whole Research attempt. Active siblings prevent aggregate terminalization. All incompatible profiles settle to configuration blocked before dispatch, with a typed pre-dispatch message notice. Completion/partial delivery require retained readable evidence and a matching saved answer. No-evidence failure and retained-evidence delivery failure remain separate, so a report-only retry does not repeat accepted acquisition.

## Schema 45: accepted policy storage

The repository was already at Chat Room schema 44. The new **44→45** migration preserves existing migrations, including 40→41, and adds `run_policy_snapshots` plus `agent_run_policy_refs`. Migration backfills recognized inline requested-policy/work-plan fragments. Unsupported legacy schemas and invalid historical seals stay inline without modification.

A canonical row is scoped to its owning chat and content SHA, and includes schema version, kind, policy revision, task digest and captured authority digest. A run stores a versioned literal/reference template bound to run ID, chat ID and user-message ID. Nested work plans reference the shared requested policy. Reconstructing the literals preserves key order, whitespace and escape spelling; both fragment and full-snapshot hashes are checked, including the original `synthesisKey` seal. No current configuration is substituted for missing accepted data.

Both public run DAOs hydrate their existing API return values. Execution/retry lookups fail with a typed saved-policy error on corruption. Observed run flows resolve on IO and isolate the damaged row into an explicit blocked projection, so saved answers and valid siblings remain readable. Startup recovery skips invalid saved-policy rows instead of automatically dispatching them. The bounded immutable reconstruction cache can only return data after current database links and exact canonical rows have been fetched and compared.

DAO hydration also prewarms the immutable typed `CombinedAcceptedTurn`/context cache on IO. Exact raw bytes are compared under their SHA key; whitespace-distinct records cannot alias. Retention is bounded by both 24 entries and four million source characters, with explicit chat/privacy deletion eviction. `CombinedAcceptedTurnCacheTest` verifies object reuse, byte distinction, bounds, legacy default compatibility and shared eviction. This reduces repeated policy parsing in UI consumers; frame-time improvement still requires device traces.

New temporary chats keep inline snapshots and create no canonical policy rows. Changing a normal chat to temporary expands valid refs, removes canonical links/orphans and clears the cache in the flag-change transaction. A damaged reference cannot prevent privacy revocation and is never replaced with a guessed payload. Chat deletion cascades rows; removing the final run link collects orphan policy bodies. The production database callback installs the cleanup trigger for fresh databases as well as migrated ones.

Complete backups include both new tables in the agent-history section. References are validated **before** destination data is removed. Legacy inline imports normalize inside the import transaction. Temporary source rows are excluded from policy validation and removed from the backup copy; a damaged private history cannot block an unrelated normal-chat backup. Public export readers expose hydrated legacy-compatible bytes, while debug export independently interns redacted policy data.

`RunPolicySnapshotPersistenceTest` covers nine runs sharing one requested policy and one work plan, all public read paths, cold migration/reopen, seal preservation, cache invalidation by missing records, non-crashing observable corruption, readable answer history, partial backup references, rejection before destination replacement, legacy inline imports, unknown policies, normal-to-temporary conversion, temporary backup pruning and last-owner orphan cleanup.

If strict policy hydration fails after a run has become active, the coordinator uses the existing raw ownership-fenced terminal update. It preserves saved text and usage instead of entering the failing policy-dependent message commit again. The regression `policyFailureAfterRunningProjectionTerminalizesOnlyTheOwnedRunAndPreservesSavedAnswer` verifies that the raw run leaves `RUNNING`, the provider is never called and no replacement answer is written.

## Validation status and remaining empirical gates

The integrated Kotlin/KSP, migration, unit, constrained-heap, lint and APK verification results are recorded in the [branch-wide validation record](Stability_Implementation_2026-10-24.md). Test presence alone is not the evidence for those results.

The following outcomes require a device or live endpoint and are **not measured by this record**:

- ROG Phone 9 Pro and a lower-memory device: queue longer than 60 seconds behind a real local benchmark, release after acknowledged cleanup/checkpoint, and observe the subsequent interactive dispatch.
- Measured feedback/dispatch budgets (500 ms/1 second) and actual queue-to-dispatch latency under device load.
- Frame traces establishing whether cached screening/policy preparation reduces the observed frames over 100 ms; no claim that the old 198.54 ms stall is eliminated solely by source changes.
- Native worker termination, GPU/CPU isolation, process death during an actual provider request and remote reconciliation with the selected service.
- Background WorkManager/notification lifecycle, screen-reader behavior, large fonts and dark/light contrast on the target device.
- Live citation/number grounding and provider capability/error behavior beyond captured fixture contracts.

The file-based accepted authority, Room conversation state and benchmark store remain explicit independent authorities with tested reconciliation boundaries. There is no claim of one database transaction across all three stores, nor of complete semantic evidence verification from lexical coverage.
