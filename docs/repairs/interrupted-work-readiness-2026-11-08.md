## Recovery contract

Three operations have different authority and replay rules:

| Operation | Implemented boundary |
| --- | --- |
| Replay a physical provider request | HTTP acceptance and assistant payload prohibit blind replay. Generation completion, request acceptance and remote tool mutation certainty remain separate facts. |
| Continue unfinished model work | Persist the completed tool boundary before generation, including an empty visible draft. Use the original profile, selected model, repository binding, saved receipts and pending-action context. A typed interruption can claim one bounded automatic continuation after usable connectivity returns. |
| Reattach to a gateway job | Require its acknowledged gateway job identity and existing reconciliation rules. A direct provider request without an acknowledged job cannot enter gateway reattachment. |

The checkpoint identifies waiting for connection, saved-result continuation, approval and uncertain remote outcome separately. Approval and reconciliation block automatic continuation. Repeated attempts without evidence progress retain the existing bounded no-progress guard. Progress narration is deterministic factual text derived from receipts; it does not spend a small model-output allowance on hidden reasoning or change substantive profile settings.

## Earlier-review follow-ups

The review-compatibility path now returns typed supported, unsupported-format or unavailable results. Only an actual format incompatibility enters the negative cache. A transport, admission, capacity or host prerequisite failure retains its original category, stage, dispatch and acceptance facts instead of being converted to “reviewer incompatible.” Optional compatibility probes cannot erase the selected model or reasoning policy.

The gateway still uses exact-model properties queries with `autoload=false`; that correct behavior is not removed. `prepare-model` is a separate explicit host command that sends at most one supported router load request and reconciles a lost acknowledgment by reading exact model state. Passive readiness never loads or substitutes a model. The operator procedure, backend compatibility limitations, host GitHub prerequisites and inference qualification steps are in [gateway/DIAGNOSTICS.md](../../gateway/DIAGNOSTICS.md).

Client diagnostic acknowledgments now identify capture-disabled and invalid-metadata dispositions explicitly. Routine accepted transport does not assert captured inference evidence. Existing build/package identity, physical HTTP IDs, causal timing, route categorization, control-surface admission and complete scoped export repairs remain on this branch.

## Gateway chat home and offline delivery

The follow-up user request adds a Gateway home using the same toolbar, navigation tabs, chat rows and New Chat control as the ordinary home. Chats, Gateway and Favorites have fixed positions from the first frame. Gateway visibility no longer waits for a successful network probe. The view includes saved local Gateway chats, their queued/running/reconciling state and the existing remote conversation history. Opening a local row opens the original chat even when the gateway is offline.

New Chat selects the sole eligible saved profile directly or presents a profile/model picker when several are available. Eligibility requires exact-configuration evidence of gateway support; an Ollama or llama.cpp provider label alone is insufficient. Remembered support permits offline creation but does not authorize dispatch. Each conversation and queued turn retains its accepted profile, model and configuration identity. Configuration changes produce an explicit blocker instead of sending to a different destination.

Gateway messages enter the existing durable prompt queue. A persisted global dispatch lease, created in the same transaction as the accepted turn, serializes Gateway jobs across conversations and process restarts. The next job waits for the preceding job's trusted terminal outcome. A lost submission acknowledgment triggers read-only reconciliation; it never authorizes another submission. An established terminal outcome frees the global execution slot even if transcript synchronization fails, while a separate durable delivery gate keeps later messages in that same chat from losing the previous reply's context. Approval, unknown remote outcome and restored-backup state remain separate from offline waiting. Ordinary provider conversations retain their existing queue behavior. Gateway chats are excluded from the ordinary home's automatic archive quota so an unsent message cannot disappear through that policy.

Opening an existing ordinary gateway conversation adopts its exact retained route and model into the serial queue. Existing engineering and Combined conversations retain their original mode, approval cards and continuation workflow; they are not converted into ordinary inference chats. Their gateway admission still respects an active queued dispatch. An ordinary conversation whose original profile cannot be verified remains readable with a precise sending blocker. A failure to persist the queue boundary cannot fall through to direct Send. The chat shows the saved queue state and provides a read-only job check plus cancellation only for work proven not submitted. A later canceled attempt cannot overwrite earlier command-dispatch uncertainty.

The process-scoped monitor retains its state while navigating between screens. Idle metadata checks run approximately every 180 seconds, with shared probes, bounded backoff and immediate invalidation on relevant network/configuration changes. Active queued work uses the faster readiness observation policy. Stale status is labeled with its last-check time and is not treated as fresh dispatch permission. Android can suspend or terminate the process; a constrained background worker provides a later wakeup, and startup restores durable work. This is not an exact three-minute promise while Android has stopped the app.

Acceptance must cover offline creation and queued input, multiple chats competing for one slot, reconnect and restart, lost acknowledgment, cancellation, changed profile/model, backup restore, opening every queue state into its original chat, and an always-present Gateway tab. Full Compose/Hilt/Room compilation and Android lifecycle behavior remain subject to the build/device qualification below.

## Validation and deployment boundary

The recorded local suites compile current production algorithms with explicit Android, Room, vault or service boundary adapters. They exercise behavior rather than testing source text. They are not a substitute for the complete Android compiler, Hilt graph, Compose runtime or WorkManager integration. Exact commands, counts and final CI state are recorded in the adjacent task JSON.

The local environment has JDK 17 and cannot download the pinned Gradle distribution; it does not have the required JDK 21/Android SDK 37 toolchain. Full Android validation therefore depends on the branch workflows or a correctly provisioned build host. Skipped or unavailable checks must remain distinct from passing checks.

Before claiming device qualification, test interruption after headers/reasoning and after visible output, completed reads, uncertain mutation reconciliation, background/restart restoration, exact approval card restoration and one continuation after approval, successful/skipped-only CI completion, semantic catalog refresh, both MCP lifecycles and owned fixture cleanup. Use the exact APK and gateway source identities. Measure release frame latency, main-thread work, export duration and retained memory on a paired workload; the debug archive and host tests cannot establish a numerical performance improvement.
