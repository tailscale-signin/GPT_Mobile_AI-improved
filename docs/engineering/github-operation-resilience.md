## Write recovery

A lost response is not permission to repeat a write. Commit recovery reads the working branch ref, the candidate commit, its parent, and both complete recursive trees. It requires the original parent and message, the intended UTF-8 blob hashes and file modes, every unchanged tree entry, and a second matching ref observation. Additional changes, a moved head, a truncated tree, and an unchanged head cannot establish success. Recovery describes an equivalent remote state without claiming which client created it.

Verified recovery completes the task claim and the exact retained HTTP ref-update claim. Concurrent reconciliation preserves the first authoritative receipt. Nested transport accounting prevents a rejected final queue admission from releasing a compound operation that already accepted or may have sent earlier mutations. Proven unsent admissions can be retried explicitly.

Branch creation reads the target ref before POST, reports an existing branch and its exact head, and never overwrites or silently selects it. A race that returns a reference collision is reconciled with another ref read. Local staging already uses deterministic stage identities; committed or submitted versions keep their original receipts.

Commit receipts include file status, previous blob identity, new blob identity and result bytes without replacement content. Staged publication also returns its retained bounded preview and validation. These receipts support subsequent edits without confirmation-only file reads. Reads needed to establish publication safety remain necessary.

Unreferenced Git objects whose creation response was lost cannot always be proven from the branch. Those cases remain blocked for reconciliation; this change does not blindly recreate commits or automatically release an unknown claim.

## Contracts and API projection

Only issued saved-view cursors can retrieve a page. Evidence handles cannot paginate search/listing operations, and a guessed fragment offset cannot skip captured records. Account, connection, conversation, operation and retained context checks still apply. Internal native continuations remain generated by the existing adapter after captured pages are consumed.

`github_pr action=headers` and `github_issue action=headers` use fixed GraphQL selections containing only header fields. They omit bodies, comments, review threads and diffs from the actual API query. A header receipt explicitly does not verify merge readiness. The tool contracts recommend these actions for metadata questions; full context and merge-health actions remain available when required. Existing REST list operations still use GitHub's REST response shape, with local output projection; local projection alone does not reduce upstream bytes.

## Worker and packaging boundaries

The Android API scheduler has bounded capacity and a cancellable 30-second queue deadline. Timed-out waiters release any racing permit, record an admission rejection and do not dispatch a request.

The diagnosed GenieX packaging common pool belongs to a Gradle JVM on the CI runner. It is separate from the Android GitHub API scheduler. The shared Android build runner now gives packaging two common-pool workers rather than reintroducing the single-worker constraint. Shrinking remains bounded to one worker and packaging runs in a fresh process.

A build deadline covers dependency retries and their backoff. Expiration terminates the process group, then kills surviving descendants after a grace interval, returns 124, and never retries the timed-out packaging attempt. GenieX's internal 86-minute package deadline leaves time inside its 90-minute workflow step for metrics and diagnostics. Existing heap/thread watchdog capture and artifact audits remain enabled.

## CI watching and errors

`github_watch_checks` remains the asynchronous model-facing interface: subscribe once, then let native workers update the chat. The receipt identifies `ANDROID_BACKGROUND_POLLING` and states that model polling is unnecessary. These workers do not receive GitHub webhooks; a true webhook transport requires a separately configured server endpoint. Persisted polling backoff grows from 30 seconds to 15 minutes, respects later server deadlines and remains bounded by a 24-hour watch lifetime. Exact-head and closed/merged-PR checks remain in place.

Typed failures distinguish primary quota exhaustion, secondary throttling, credential authentication, endpoint permissions, SSO, branch rules, conflicts, validation and transient server/network failures. An unexplained 403 remains unexplained. Native engineering transport inspects bounded error text privately; a secondary-limit 403 without Retry-After receives a cooldown instead of terminating the watch as a permission failure. Ordinary quota-reset headers do not authorize permission retries. Rate-limit categories also stop repeated model tool attempts during the same response. No category authorizes automatic mutation replay.
