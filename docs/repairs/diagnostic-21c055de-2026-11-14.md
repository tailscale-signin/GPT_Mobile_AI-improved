## Source repairs

### Keep graph preparation from starving other verification

The self-test planner previously placed each new graph-index cursor ahead of independent reads at the same priority. A large repository could therefore spend many batches on indexing while repository and workflow dependencies waited. Independent reads and workflow-definition dependencies now precede each index batch. Saved-status reconciliation retains priority when an earlier indexing outcome is unknown.

Graph indexing, including its background job controls, remains a state-changing action. A read-only wrapper cannot grant replay authority to that action. A deadline or lost response preserves the exact checkpoint and requires matching saved-status acknowledgement before another index operation can proceed. The authorization change retains the user's existing local graph permission while preventing an uncertain action from being repeated.

### Preserve GitHub capacity for foreground work

The gateway now consumes valid observed core quota metadata from successful responses. Source-tree/blob admissions reserve 100 remaining requests for foreground work. This is a local indexing reserve, not an assumed GitHub quota or a promise of account-wide capacity. Missing, invalid or expired quota metadata cannot create a fictitious quota observation.

When a source batch encounters a rate wait, completed sibling fragments are saved and throttled files remain pending. The durable index job keeps its revision and cursor, releases its worker and records the retry deadline. Quota waits do not spend the transport retry allowance or become parser failures. Ordinary permission failures still remain failures. Pausing/resuming or canceling/restarting the same revision cannot discard an unexpired quota deadline. A wait beyond the job budget wakes the worker to pause the expired job without making a source request; the full server wait is retained.

Local reserve pauses and actual upstream rate responses remain distinct. Graph HTTP routes retain a bounded reason and Retry-After instead of flattening every rate wait into generic connection failure. Status, cancellation and foreground work retain their ordinary authority checks. Structured rate responses apply only to graph routes. Other job-admission routes retain their existing unknown-outcome response, including when a command was durably accepted before the response failed.

The wait policy follows GitHub's [rate-limit guidance](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#handle-rate-limit-errors-appropriately): respect Retry-After, respect the reset time for an exhausted resource and use a bounded fallback when the server supplies no usable deadline.

### Retain the cause across Android tool and report boundaries

- Distinguish local `GITHUB_COOLDOWN_ACTIVE` admission from an actual primary/secondary GitHub HTTP rejection. Retain the observed resource, remaining quota, sampling time, reset/Retry-After basis and retry deadline. A local rejection does not invent an HTTP response or erase an earlier dispatched operation.
- Keep the later of the exhausted-resource reset and shared cooldown deadlines. A shorter Retry-After value no longer advertises an earlier retry while the resource remains exhausted.
- Preserve graph checkpoint uncertainty through the repository callback, tool result, accumulated dispatch receipt and incident projection. A successful status request can still leave the earlier index outcome unconfirmed.
- Retain observed gateway HTTP status/Retry-After and bounded caught exception fingerprints/types without payloads, credentials or raw private identifiers. Native context failures preserve the actual caught cause instead of reducing every rejection to `GITHUB_OPERATION_FAILED`.
- Keep selected-profile rejection typed as `GITHUB_PROFILE_LOCKED`, with separate profile-match, registration and model-match observations. The selected model and existing dispatch admission condition remain authoritative.
- Put recorded failed operations first in the bounded acceptance-report sample, then include distinct prerequisite blockers. Original counts, omissions, acceptance states and approval conditions remain intact.

The new exact HTTP-header helper applies to REST requests. GraphQL retains the typed cached-admission cause but does not acquire the new response-evidence helper.

The hosted reporter negotiates `GH_COOLDOWN_V1` and `PROFILE_SELECTION_EVIDENCE_V1`. Native authenticated GitHub submission remains independent. Unsupported hosted services retain the approved payload and require a compatible service before submission; the app does not silently strip approved evidence.
