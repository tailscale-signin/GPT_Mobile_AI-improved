# Premium experience implementation and acceptance

PR #1741 brings the five phases into the existing Android app and Windows Gateway. The table identifies the entry point and the observation needed to qualify each change for release. A source implementation, an emulator run and an observation on the paired phone cover different conditions.

| Step | Implementation on this branch | Release observation |
| --- | --- | --- |
| 1. Reliability | Provider context rejection handling, model-specific cooldowns, tool schema repair and GitHub mutation reconciliation. Conflicting explicit context limits use the smallest valid limit. | Exercise the selected provider's context and rate-limit responses. Check that uncertain writes remain fenced until reconciled. |
| 2. Continuity | Saved Gateway commands, conversation revisions, durable tool checkpoints and restart reconciliation preserve the original work identity. | Reopen the same answer after network loss, an Android force-stop and Gateway restart. Match its command, job, message and content. |
| 3. Context | Route and local runtime capacity discovery, catalog evidence, protected instructions, complete-turn retrieval and final request budgeting. Unknown capacity uses the route's fallback. | Exercise large histories against a small loaded model, a remote catalog profile and a profile with unavailable metadata. |
| 4. Connected acceptance | Android instrumentation, GitHub live acceptance, Gateway tests and the physical connected-chat collector have independent entry points. | Capture the phone, build, selected profile, fixture repository, Gateway identity and original command. |
| 5. Shared chat | Standard, Combined, Research, Local and GitHub conversations use the common composer, header, answer rendering and scroll-follow rules. | Switch modes and verify composer focus and reading position during streaming. |
| 6. Narration | The common activity feed uses task-specific openings, public checkpoints and coalesced counter updates. | Run a quick question and a multi-tool investigation. Verify that narration tracks observed work. |
| 7. Progressive answers | Streamed prose and code share the same answer surface. An unfinished native component shows a compact placeholder until its closing fence arrives. | Observe useful answer text and a finished component before the stream ends. |
| 8. Intelligent UI | Versioned answer data supports metrics, sortable tables, bars, places, source links, navigable relationships and CSV. Generated images and sandboxed previews use the existing media and artifact flows. | Supply known values, negative changes and malformed data. Verify what appears, sorts, exports and opens. |
| 9. Motion and access | Shared reduced-motion, bottom anchoring, themed controls and accessibility semantics. Metric cards wrap and group each value with its label. | Check TalkBack, large fonts, landscape and frame times on the target phone. |
| 10. Routing | New Chat offers Auto, Fast, Think and Research, alongside direct profile selection. Auto can match an optional first message locally to quick, reasoning or explicit research work. Its label shows the suggested mode. The confirmed chat saves the message as an unsent draft. Suggestions use eligible profiles, successful measured latency, completion history, cost and available context. Research prerequisites also apply when choosing Fast from Research. Saved messages expose recorded model identity. | Check local and remote choices with failed, missing and stale benchmark evidence, then inspect the serving model in the saved answer. |
| 11. Projects | Project instructions, documents, chat membership, default profiles and memory preferences live together. Creating a copy or an edited branch carries project membership in the same Room transaction. | Duplicate a project that excludes personal memory. Confirm the new chat sees only its permitted knowledge. |
| 12. Research | Source inspection, captured passages, counterevidence, claim grounding, retained report drafts and continuation are available in Research. The Gateway can watch for new publications. | Resume an interrupted report with conflicting sources and inspect citations against captured passages. |
| 13. Multimodal | The attachment menu accepts audio and documents. A PDF-capable route receives the original scan. “Attach scanned PDF page” stages one chosen page as an image for transcription or visual analysis by the selected vision model. Generated images can return to the same chat for editing. | Check a scan, recorded audio, original image and authorized image edit on each selected capable profile. Recognition quality depends on the model. |
| 14. Voice | Capture and playback remain in the same conversation. Live captions use actual engine range callbacks when supplied. A bounded word lookup supports long replies and supplementary Unicode letters. | Measure first audible output, interruption, recovery and timing with the installed speech engine. |
| 15. Autonomous work | The engineering agent records plans, scoped approvals, execution checkpoints, verification evidence and final reports. Uncertain writes require reconciliation. | Use a disposable repository and verify approval, interruption, recovery and the intended side effect. |
| 16. Durable work | The Gateway schedules reminders, storage checks, public research watches and approved repository tests. It stores unread alerts transactionally and reports actual lease or terminal state. | Close the desktop window across an occurrence, reopen the schedule and read the alert. Acknowledging it preserves later occurrences. |
| 17. Artifacts | The offline analysis workspace imports bounded JSON/CSV, exports data, documents, spreadsheets, presentations and plots, and saves editable Python and input. A user can request a code revision in the original chat and rerun it against the same data. | Use the configured offline sandbox. Confirm that edited code requires a new run, stale results cannot export, and switching chats preserves the destination. |
| 18. Evaluation | CI publishes fixed named behavior outcomes in the app-audit report. Android Macrobenchmark measures fixed rendering scenarios. The connected-chat collector compares two builds using the same handset, OS, Gateway principal and saved answer. | Collect same-device latency and frames, unplugged charge when available, observed provider usage/cost, grounding and task results. Report missing hardware or provider observations explicitly. |

## Reproducible comparisons

Run `scripts/qualify_connected_chat.py --help` on the paired Gateway for the required fixture arguments. Save the baseline JSON before updating the app. Repeat with the original arguments, a new output file and `--baseline <first-report.json>`. The result gives candidate minus baseline in milliseconds and, when both runs have a discharging-battery reading, microampere-hours of whole-device charge. A negative time difference means the candidate reopened the answer sooner on that pair of observations. Repeat comparable sessions before drawing a performance conclusion.

Use `scripts/qualify_device_performance.py` for Macrobenchmark comparisons and `scripts/github_live_acceptance.py` for the authorized GitHub fixture. The Android CI artifact contains the specific test and report hash for each verified JVM journey. Model quality, physical voice latency, paid provider cost and paired Windows recovery need their own observations.
