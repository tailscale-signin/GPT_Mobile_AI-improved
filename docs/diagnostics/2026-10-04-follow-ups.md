# Diagnostic review and concurrent follow-ups

Reviewed `app-diagnostics.log`, 3,969 lines, captured 2026-10-04 14:10–14:34 UTC. The capture ends during an active delegate request, so the final outcome of the last conversation is unknown. No private prompts or network addresses are reproduced here.

## Findings

1. **Repeated reasoning-only completions waste substantial work.** There are 10 reasoning-only repairs and one output-cap repair. The local worker repeatedly spends its original 2,048-token cap on reasoning, then receives an 8,192-token repair request. The second run ultimately reports 26,212 wasted tokens and 133,771 ms of waste, including 24,460 repair-waste tokens. Prefer a concise/no-thinking worker preset where supported, and learn the appropriate cap from observed usable-output requirements instead of repeating the same unsuccessful cap.
2. **Review rejection is real and costly.** The first run passes with score 80. The second run is rejected at scores 30, 35, and 20, and fails after approximately 8m11s of preparation. This is not the earlier false-success-as-error bug. Expose the review issues, impose a whole preparation budget, and stop escalating when repairs do not improve evidence quality. Reviewer calls have zero child tools, which confirms role isolation for these requests.
3. **Reviewer usage estimates disagree.** At log lines 2,889–2,891 the invocation ledger estimates 4,199 output tokens while the child summary estimates 201 usable output tokens and 2,949 reasoning tokens. Distinguish visible output, reasoning, and total compute consistently. Missing provider usage is not an enforced-cap violation by itself.
4. **Page accounting is questionable.** Preparation reports `pages=0` despite numerous page reads and 139–158 KB of raw evidence. Investigate whether this field counts attempted, extracted, retained, or accepted pages. Log each count separately rather than treating zero as proof that no reads occurred.
5. **Blocked sources are retried unnecessarily.** Nine HTTP 403 page-read warnings include repeated attempts against the same site. Cache denial per host within the research run, select alternative sources, and avoid spending a fresh read allowance on the same denied host.
6. **HTML clipping may discard useful article content.** There are 61 bounded oversized-source warnings; later allowances shrink to 4,096 bytes. Extract article text before choosing evidence snippets, and include truncation/coverage flags in the handoff. Prefix-clipped markup can consume the allowance before the article starts.
7. **Binary sources have no useful fallback.** Three page reads reject binary content. Prefer an HTML/text version or a cached abstract and explain the limitation. Do not count the unread source as verified.
8. **The gateway is responding, but deadlines still interrupt a repair.** Numerous gateway requests receive 200 responses. One delegate repair ends in `Request timed out` around line 2,610. Both first-progress and idle deadlines equal the entire 45/90-second runtime, limiting their usefulness as separate watchdogs. Two retries join gateway singleflight followers, so distinguish reused compute from fresh retries when reporting waste.
9. **Research classification can miss the initial request.** The final run declares `NO_RESEARCH_NEEDED`, then starts further delegated research during primary generation. Examine planner input and confidence, and allow a low-cost correction without repeating the entire preparation pipeline. The log ends before this work completes.
10. **Rendering needs profiling.** Across 316 frame samples, 3,554 of 37,920 frames are labeled janky (about 9.4%). The maximum reported frame time is 164.35 ms. These are aggregate timings, not proof of a specific cause. Profile streamed markdown, trace detail updates, and recomposition under the phone's 6.06 ms frame budget.
11. **The main coroutine method is too large for Android compilation optimization.** Two messages report `Method exceeds compiler instruction limit: 41888` for `completeChat`. Extract stages into smaller methods. The new follow-up integration keeps its orchestration in a separate method and its stream coordination in a separate class.
12. **Log volume obscures useful signals.** Repeated frame and header dumps dominate the capture. Aggregate frame metrics over larger windows, retain anomalies, and report separate latency, time-to-first-token, extraction, and reviewer counters. MCP health latency `-1` should display as unavailable, not as a real latency.

## Implemented behavior

- Eligible text queued during a primary model request starts a separate, bounded follow-up worker while the original request continues.
- The worker receives the addition and a 1,600-character original-task excerpt, not the full conversation. It uses at most three inherited read-only tools, a two-call tool allowance, a 4,000-token estimated input ceiling, a 768-token output ceiling, and a 45-second timeout. Recursive delegation, gateway-owned extra tools, and automatic 8,192-token repair escalation are disabled for this role.
- The configured delegate is used only when its destination is authorized and it is not the reviewer. Otherwise a separate request uses the active primary profile.
- At a safe provider boundary, compare-and-transfer accepts the exact current queue snapshot into the original user message. Edits, removal, pause, model/tool changes, or canceled parents cannot silently consume stale input.
- The primary continues in the same assistant message using the original-task excerpt, accumulated compact follow-up handoffs, and the last 6,000 characters already shown. It does not restart the original request or replay earlier chat turns. Pending primary tool calls execute before continuation. Each physical primary request has its own ledger reservation and usage accounting.
- At most three additions are merged per active answer, with bounded cumulative context. Oversized input, attachments, multi-profile queues, batch/free/on-device sessions, and budget-ineligible additions remain durable for ordinary queue dispatch.
- A failed/timed-out helper can hand the raw user addition to the primary without claiming research. Input remains in history after acceptance; input not accepted remains queued.
- Queued bubbles use gray backgrounds and lighter italic text. Search/ready states are visible. Acceptance triggers a theme tint, three 500 ms opacity transitions, then a 650 ms upward shrink-and-fade animation. Animation never blocks generation.
- Expanded debug details show the follow-up prompt and result in bright teal. Collapsed cards retain ordinary colors.

## Additional diagnostic fixes

- Reasoning-only worker output gets one concise retry at the original cap. Subsequent requests for that model use concise transport settings. Truncated visible output gets at most one 2× finalization request, bounded to 4,096 tokens and the profile limit.
- The configured discarded-token ceiling is enforced without ownership-based inflation, including before retries and between a failed request and its repair. A turn-wide preparation deadline defaults to 180 seconds; review/correction has its own 90-second aggregate deadline. Both are configurable. Regressing/equal review scores or unchanged corrections stop further correction calls; rejected evidence stays unverified.
- Missing usage uses the same UTF-8 byte estimate as context planning and the ledger, including reasoning. Explicit provider zero counts are preserved and estimated fields are labeled.
- Search-owned page reads now contribute to attempted/retrieved/accepted page counters and the research handoff. Search crawling caches URLs for the turn, shares a page allowance, and stops after the first usable reader instead of reading every selected crawler.
- Read-URL remembers 401/403 denials per host during the turn. HTML extraction uses a bounded 1 MiB body before applying the evidence allowance, prefers article/main text, and removes navigation/header/footer material. Long legitimate article text is no longer rejected solely because it mentions multiple consent terms. Binary sources remain explicitly unread.
- Streamed-markdown fade updates stop once arrivals settle and discard expired fade segments; placeholder identity stays stable during streaming. Frame diagnostics run off the main thread and report at five-second intervals, using the platform frame deadline when available. Primary answer streaming is extracted from `completeChat` to reduce its coroutine size.
- The reported 9.4% jank rate and compiler warning require a new APK/device trace to verify. These changes address likely overhead and method size; they do not establish a measured performance improvement.

## Efficiency limits

Stateless APIs cannot insert new input into an already-running request. A bounded continuation is required and incurs new input/output tokens. The implementation avoids replaying full history or regenerating the answer already shown; it does not claim zero extra compute. Existing prepared system context remains available to the primary. New follow-ups are admitted while provider requests run; messages arriving after admission closes remain queued. Worker output is evidence, not a substitute for the user's instruction.
