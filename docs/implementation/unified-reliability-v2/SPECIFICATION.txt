Capacity and measurement
Use the configured direct/router/gateway route. Key discovery by connection/credential revision, selected and resolved model, runtime epoch, template/tokenizer and allocation policy. Never infer serving capacity from a catalog alone or blindly divide global context by slot count. Optional llama.cpp endpoints are capability/version-gated; missing /props does not mean chat is offline. A proposed gateway preflight API is a project extension, not an existing llama.cpp API. [LC §§4–5; W01]
Prefer the serving tokenizer plus matching template. A local tokenizer is exact only after parity tests, including tools, reasoning and special tokens. Otherwise label the estimate and uncertainty. Freeze an internal request digest without logging secrets; exported redacted digests describe that different representation. Gateway transformations must have a separate verification boundary or remain explicitly unverified. [LC §§3–5; CM §11]
Settings precedence and recovery choices
First honor destination/privacy constraints and verified runtime limits. Resolve user-explicit maxima and request-role restrictions separately from a desired answer target. An inherited application default cannot masquerade as an explicit user maximum. Null/zero legacy settings mean no extra app cap where that was their prior meaning, never zero output or infinite runtime. Reasoning AUTO/ON/OFF resolves against actual backend/template capability; requested, transmitted and observed states remain separate. [R08–R11; LC §8]
Remove irrelevant schemas, repeated wrappers and exact duplicates first; then apply the visible retention policy only to lower-priority history. Preserve tool-call/result pairing. If required content or output cannot fit, return a typed shortfall and keep originals unchanged. Offer only an authorized segmented workflow or explicit larger-context selection. No silent primary substitution or cloud fallback. [LC §§5–6; CM §§4–5]

07  Scheduling, progress and recovery
A timeout is not proof that native code has stopped.
Phase
Required behavior / proposed initial policy
Resource scheduling
One owner per resolved backend domain; start at one active generation until concurrency is qualified. Share that owner across Assist, primary, delegates and title work. Fair queues, bounded age/capacity, foreground priority with starvation protection.
Queue / preparation
Separate queue, load, prefill, first progress and decode clocks. Preserve existing user limits. For desktop unknown queue/load timing, start with visible 180-second policy; adapt only with observations.
Prefill / first progress
Use uncached tokens, measured conservative prefill rate and cold-load overhead where available. LC proposed initial adaptive bounds 60–600 seconds; no-progress fallback 180 seconds. These are calibration values, not guarantees.
Thinking / generating
Begin with proposed 90-second meaningful-progress idle allowance; count nonempty reasoning/text or advancing native counters. Ignore pings, repeated stages/counters and empty chunks. Remove unrelated fixed 180-second round cutoff.
Total run
Honor the explicit user-configured generation deadline; preserve the existing setting and its migration semantics. A reasoning-only response is active but is not a completed visible answer.
Cancel / timeout
Signal actual transport/native cancel, remove queued descendants, persist one terminal outcome, and bound cleanup. Keep native lease until acknowledged stopped or isolated process terminated; quarantine a stuck session.
Shared work
Do not cancel physical work still authorized by another subscriber; cancel once all subscribers leave. Release generation permits during external-tool waits; never hold the only permit while waiting for a child needing it.

Separate recovery branches
Zero-visible output exhausted: restart answer writing from the original frozen corpus and complete outline within authorized settings, not 'continue after the last section.' Partial visible output: continue after committed segments without replacing the prefix. Clean provider stop with missing requirements: coverage repair or explicit incomplete state. Interrupted stream: reconcile saved work; never replay a possibly executed write without status reconciliation. Cancellation/revocation: no automatic retry or fallback. [LC §§7–9; CM §6; W03]
Persist stage-specific failure codes: CONTEXT_INSUFFICIENT, CONTEXT_UNVERIFIED, OUTPUT_LIMIT_INVALID, MODEL_LOADING, BACKEND_BUSY, GENERATION_STALLED, RUN_DEADLINE_EXCEEDED, STREAM_INTERRUPTED, BACKEND_RESOURCE_EXHAUSTED, LOCAL_ENGINE_INCOMPATIBLE, USER_CANCELLED and PERMISSION_REVOKED. Preserve unknown sanitized provider errors; not every HTTP 400 is a context failure. [LC §9]

14  Rollout, rollback and handover
A deployment flag may disable behavior; it must not erase evidence or safety checks.
Controlled rollout
1. Instrument existing behavior first: scoped decisions, truthful budget phases, cap-origin tracing and terminal outcomes. Do not display shadow decisions as proof of a dispatched request.
2. Enable final admission and presence-aware settings, then shared scheduling/progress/recovery. Verify every role and exact outgoing request before allowing experimental optimizations.
3. Enable typed evidence and Assist task execution with original-evidence fallback. Qualify the intended model/backend/device combinations; leave unsupported combinations unavailable with actionable reasons.
4. Enable Combined full context, slot ownership, durable segments and coverage before color attribution. Run shadow attribution only inside approved data/cost scopes.
5. Enable detailed diagnostics only after redaction/temporary-chat tests. Full-content capture remains separately consented. Turn on optional compression/adaptive tuning only after paired coverage/cost/latency tests.
Rollback guarantees
Independent flags may revert heuristics, Assist execution, Combined assembly, coverage, attribution or content capture. They must not turn off known runtime context ceilings, live permission checks, stable output ownership or honest degraded-state reporting. Keep newly written schemas readable; do not downgrade destructively or delete source artifacts needed by surviving answers. Loss of optional logging is distinct from loss of operational persistence. [LA §17; LC §14; CM §15]
Required final implementation report
State the exact branch/commits, version/code, build variants and database schema. For every task, link implementation and test evidence; list any BLOCKED case without euphemism. Report long-input preservation separately from answer recall/length; report attribution precision/recall/abstention and comparison coverage; report measured app overhead separately from provider time.
Publish the tested hardware/artifact/backend matrix, settings migration behavior, rollback exercise, redaction/export integrity and declared limitations. A failing or unavailable qualification does not become a supported feature because another backend passes. An explicitly approved partial release must name the deferred scope and cannot claim full compliance with version 2.0.
Implementation pack
Use TECHNICAL_DESIGN.md as the canonical portable specification and EXECUTION_BRIEF.md as the agent handoff. tasks.json, acceptance-tests.json and requirements-coverage.json carry stable IDs and evidence placeholders. review-audit.json records the sanitized recheck, not application test results. validate_manifest.py checks structural completeness; --require-done additionally requires declared completion evidence. It does not execute or independently validate Android tests.
