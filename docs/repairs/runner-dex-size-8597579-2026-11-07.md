# Reduce AgentRunner coroutine size without changing execution policy

Repository: `tailscale-signin/GPT_Mobile_AI-improved`. Parent PR: #811. Base: `c285a86803e940c469ff8a4d23770547143d0511`. Work branch: `work/runner-dex-size-8597579`.

## Confirmed packaged failure

UI Review APK run `42378572880`, job `128421226468`, passed production, device-test, and benchmark compilation. Packaged native runtime, JNI, alignment, and telemetry checks also passed. The unchanged `check_research_dispatch_size.py` gate then found `AgentRunner.executeLoop` at 24,310 DEX code units (48,620 instruction bytes), above its exclusive 16,383-unit limit. It was the only oversized guarded method.

The loop carried many independent counters, maps, and repair flags across suspension points. Moving those values into one private state object avoids repeating the coroutine's save/restore bookkeeping for every value at each suspension point. Receipt restoration and round preparation are cohesive non-inline methods, so their coroutine machinery no longer enlarges `executeLoop`.

## Behavior retained

`LoopState` is constructed inside each `executeLoop` invocation, after the existing initial definition selection. It is never stored on the reusable runner or shared between flow collections. The loop body keeps its statement order, including accepted-call accounting, restored/live invocation fingerprints, recovery round adjustments, and one-shot repair flags.

`restoreCompletedExchanges` still delivers settled receipts before inference, preserves unknown outcomes, and stops immediately after an authority-invalidated receipt. `prepareNextRound` preserves the call/round thresholds, final-response allowances, notices, and round increment. Neither helper introduces a new coroutine, flow, dispatcher, retry, or exception-catching boundary. Cancellation and downstream collector failures remain transparent.

The new `AgentRunnerTest.repeatedFlowCollectionsDoNotShareLoopBudgetsOrFinalizationFlags` collects the same cold flow twice with one-call and one-round limits. Both collections must perform their own single fixture invocation and final answer, with two total tool invocations and four provider requests. This guards the state holder's per-collection lifetime.
