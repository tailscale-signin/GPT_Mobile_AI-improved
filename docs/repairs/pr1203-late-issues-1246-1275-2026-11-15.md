## Repeat admission observations

The existing source-read guard keys a repeated call by the model-facing tool name
and canonical complete arguments. It uses prior admitted calls plus provisional
admissions in the current batch. Those counts are admissions, not successful HTTP
responses. Different arguments or connections remain independent. No supplied
payload proves that the guard rejected different URLs as one repeated call.

| Field | Meaning |
| --- | --- |
| `dependency_repeat_scope` | `TOOL_NAME` or `TOOL_NAME_AND_ARGUMENTS`, as observed by the guard. |
| `dependency_repeat_prior_admissions` | Prior admissions for that exact repeat scope. |
| `dependency_repeat_batch_admissions` | Provisional admissions in this batch at the refusing decision. |
| `dependency_repeat_used` | The actual combined operand compared with the limit. |
| `dependency_repeat_limit` | The applied limit. |

The observation is captured before later dependency closure or counter updates.
It applies only to the directly refused call. A dependent child cannot inherit
its prerequisite's repeat operands. Counts retain the closed bounded integer
contract; arbitrary receipt keys cannot create a trusted observation.

Qualified projection requires matching saved call ID, model-facing tool name and
argument identity. Argument parsing and canonicalization are bounded. Private
comparison keys and argument values never enter the public report. The operands
remain in the durable receipt and approved report but are omitted from the
model-visible result envelope, preserving its previous context cost. No retry,
dispatch, finalization, admission-limit or unknown-outcome rule changes.

## GitHub conversation navigation

A saved GitHub context is the room's mode identity. Previously the router returned
the same null destination for an ordinary room and for a saved GitHub room whose
original connection or plugin was unavailable. The latter could therefore create
an ordinary chat controller before the saved GitHub context loaded elsewhere.

The router now distinguishes ready GitHub, unavailable GitHub and ordinary rooms.
The unavailable view retains the room and exact original connection identity,
explains how to restore access, and offers Plugins and Back. It does not choose
another account or grant execution permission. Both plugin enablement predicates
and the original connection's `GITHUB` type remain required for a ready route.

Ordinary rooms using a GitHub-capable profile stay ordinary. Ready GitHub rooms
retain their existing route. Existing voice-room identity and research-mode
routing remain intact. This is a source-demonstrated fallback defect; the old
report does not establish which connection or plugin state was present on the
phone.

## Durable tool-event start and failure evidence

Re-collecting a resumable chat can retain a run and its saved tool events while
recreating the caller's sequence counter. Starting a distinct call at zero can
then collide with the unique `(run_id, sequence)` index.

One Room transaction now checks for an already saved call, reads the run's durable
maximum, allocates with `Long` arithmetic, and strictly inserts the new event.
An existing call returns its original row before exhaustion is considered.
Allocation retains a higher caller sequence, never wraps past `Int.MAX_VALUE`,
and fails before insertion when exhausted. The raw insertion API, schema and
history-copy behavior are retained.

Typed persistence failures carry only observations from this local operation:

- Operation and phase: `START`, then `ALLOCATE_SEQUENCE` or `INSERT`.
- A closed reason: run/sequence conflict, event-ID conflict, run foreign key,
  not-null failure, unknown constraint or sequence exhaustion.
- Requested sequence, assigned sequence when available, and the prior maximum
  when a row existed.
- Whether this local insertion was attempted.

The original exception remains attached. An unrecognized constraint message stays
unknown; public fields exclude raw SQL, messages, arguments and identifiers.
These values say nothing about earlier tool/provider dispatch or permission to
retry the run. Cancellation and unrelated failures retain their existing paths.

The generic SQLite category is separately obtained from a bounded actual cause
chain. Producer-reserved SQLite, persistence and repeat fields supplied only as
raw execution-receipt text are excluded from report projection. The original
stored receipt remains intact for its existing uses.

## Acceptance observations and compatibility

Receipt trust retains its existing requirements. Optional diagnostic observations
record the actual failed predicate without promoting an untrusted receipt or
changing model/review budgets. The optional marker must not change whether the
original receipt fits its existing storage or chunk boundary; when it cannot be
retained within that boundary, its absence means unknown.

Publication-entry and comparison observations belong to the actual producing
snapshot. They are cleared when newer evidence supersedes it. Existing opt-in,
private-session suppression, report size limits, payload approval and exact-byte
submission semantics remain in force.

Hosted compatibility is negotiated through distinct capabilities:

- `TOOL_REPEAT_ADMISSION_EVIDENCE_V1`
- `TOOL_EVENT_PERSISTENCE_EVIDENCE_V1`
- `SQLITE_CONSTRAINT_EVIDENCE_V1`
- `ACCEPTANCE_OBSERVATION_CAUSES_V1`

The bounded extended readiness response carries these capabilities. The legacy
readiness and submission-receipt limits are unchanged. Older services keep an
approved report pending instead of silently dropping its fields or claiming
support. Updating repository source does not establish hosted-service deployment.
