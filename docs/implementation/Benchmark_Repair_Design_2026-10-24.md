# Benchmark repair design implementation — 24 October 2026

This report maps the 23 October benchmark repair design to production code and regression coverage. It distinguishes implemented behavior from hardware acceptance. **The final integrated Kotlin unit-test and lint run is pending at the time of this report; the presence of a test is not a claim that it has passed.**

Production paths below are relative to `app/src/main/kotlin/dev/chungjungsoo/gptmobile/`. Test names refer to `app/src/test/kotlin/dev/chungjungsoo/gptmobile/`, unless a different path is given.

## Execution, persistence and recovery

| Design requirement | Implementation and evidence | Regression coverage |
|---|---|---|
| Continue after the first, middle or final profile fails | `data/benchmark/BenchmarkBatchRunner.kt`: a supervised profile child is awaited by a healthy queue parent. A completed wrong answer continues independent cases; an execution failure ends only its profile and creates dependency skips. | `BenchmarkQueuePolicyTest`; real-Room `BenchmarkBatchRunnerTest.firstMiddleAndLastChildAbortsRetainRowsAndContinueTheFrozenOrder` |
| Genuine Stop, Skip and child abort have different owners | `BenchmarkBatchModels.kt` defines durable stop origins. `requestStop` writes the session/ordinal-scoped action before child cancellation. Parent cancellation propagates; a healthy parent classifies a child abort. | Queue policy parent/child cancellation tests; BatchRunner Stop/resume test; coordinator cancellation and foreground-promotion race tests |
| Every selected profile keeps one ordered disposition | Batch and queue manifest are stored before dispatch, including frozen configuration, run IDs, order and ordinal. Terminal batch state requires all items terminal; quality failures do not imply an incomplete queue. | Queue policy completion tests; BatchRunner frozen order/model assertions |
| Resume untouched items; Retry failed preserves prior evidence | `BenchmarkStore.recoverBatches`, `BenchmarkExecutionCoordinator.resumeBatch`, and `ProfileBenchmarkViewModel.retryFailed` retain interrupted attempts, completed cases, retry lineage and pending queue membership. Deleted profiles become explicit failures. | BatchRunner Stop/resume; Store process-interruption and final-case-before-advancement recovery tests |
| Keep cleanup inside measurement ownership | Each preflight/trial owns `InferenceAdmission.benchmark`; cleanup and the canonical checkpoint occur before its release. A shared 10-second boundary includes the checkpoint's preliminary read as well as its write, including under `NonCancellable`. `isNativeOperationBusy` excludes the owner's admission reservation while retaining generation-lock and unacknowledged-worker state. | `BenchmarkCleanupTest` covers acknowledged cleanup, stalled checkpoint reads and true parent cancellation; `PlannedLocalRuntimeTest.nativeBusyReceiptSurvivesThePlanningWrapper`; existing native termination/queue tests |
| No overlapping local work after unconfirmed cleanup | Bounded close requires both no native operation and no open conversation. An unconfirmed receipt blocks later local profiles; independent remote profiles can proceed. Existing worker cancellation/termination/quarantine controls remain authoritative. | Cleanup acknowledgement/quarantined-worker regression; device worker-stall injection remains required |
| Durable batch, queue, case attempts and ordered events | `BenchmarkDatabase.kt` migration 2→3 adds four tables. `checkpoint` atomically writes run evidence, changed attempts and queue state. Logical request IDs, invocation IDs and physical admission IDs are distinct. | `BenchmarkMigrationTest` uses the published version-2 SQL fixture; Store queue/attempt recovery and backup tests |
| Room is canonical; a mirror cannot roll it back | `BenchmarkStore` performs incremental canonical writes and immediately publishes committed state. Mirror writes are coalesced and optional. Corrupt mirror recovery is best effort. A canonical initialization marker uses the existing current-pointer row even when the first derived snapshot fails. | Store tests for stale mirror, failed mirror commit, corrupt mirror plus failed recovery commit, subsequent save/reopen and no resurrection after deletion |
| Derived-score failure cannot invalidate saved results | Snapshot work runs off the UI thread, uses best-effort publication and a contained maintenance scope. An observable warning reaches the screen. Snapshot deduplication and a 100-snapshot retention bound remain in the DAO. Cancellation is rethrown. | SQLite-triggered snapshot failure test verifies committed queue/runs, next save and reopen |
| Canonical failure visibly pauses instead of crashing or advancing | BatchRunner stops dispatch on `BenchmarkStorageFailure`. Coordinator checkpoints `STORAGE_PAUSED` where possible and preserves pending rows; a root exception handler prevents an observed storage exception from reaching Android's crash handler. Recovery failure prevents new dispatch. | `BenchmarkExecutionCoordinatorTest.storageFailurePausesDurablyWithoutEscapingToTheProcessCrashHandler`; queue policy storage isolation test |
| App-owned foreground lifecycle and stale action fencing | `BenchmarkExecutionCoordinator`, `presentation/service/BenchmarkForegroundService.kt` and ViewModel use the same session identity. Foreground readiness is acknowledged before execution; old notification tokens cannot cancel a successor. | Existing coordinator promotion/rejection/cancellation race tests; device notification/background acceptance remains required |

## Measurement, scoring and presentation

| Design requirement | Implementation and evidence | Regression coverage |
|---|---|---|
| Policy rejection is not an answer | `data/accounting/InvocationLedger.kt` emits benchmark-only `Failed(errorCode=POLICY_BLOCKED)` before denied dispatch. Runner retains the structured admission failure, no answer text and no invented accuracy. A denial after a tool round retains the earlier dispatch. | `InvocationLedgerTest.benchmarkAllowanceDenialsArePreDispatchPolicyFailuresWithoutAnswerText`; Runner second-round denial test |
| No hidden benchmark retry or unbounded cooldown loop | `BenchmarkRunner` defaults reconnect off. BatchRunner stops a failed profile once and records dependent skips. An explicitly enabled reconnect shares the original request deadline. | Runner no-retry, infrastructure-stop and preserved-usage tests; provider transport fixtures |
| Validate fixtures and canonical final content | Suite definitions are validated before dispatch. HTML/provider envelopes, empty/reasoning-only responses and invalid speed shapes cannot pass. Canonical answers are bounded, hashed and marked truncated; regrading refuses invented missing text. | Runner malformed expected-JSON, HTML/envelope, one-chunk answer and truncation tests |
| Actual output budgets and response schemas | `BenchmarkProfile.kt` resolves category-specific output budgets; `ChatRepositoryImpl.openBenchmarkSession` supplies constraints and the appropriate final schema. Effective request settings are retained from provider configuration events. | Profile budget tests; provider/local schema tests; root adapter regressions |
| Distinguish reported, estimated, partial and unknown usage | `BenchmarkMeasurement.kt` reuses `ProviderUsageCounter`. Final native/provider counts can replace larger early estimates. Source/confidence remains separate for input, output and reasoning counts, per round and per sample. Missing input is unknown rather than measured zero. | `BenchmarkMeasurementTest` final-native replacement, initial/estimated usage and reasoning-only exhaustion tests |
| Use elapsed timing and retain stage intervals | Production ordinary/delegation runners receive Android `elapsedRealtime`. Sequential client-observed phases include setup, load/prefill/generation, visible output, tool work and validation. Phase detail is bounded; complete phase totals survive detail truncation. Admission wait and cleanup durations are separate. | Measurement phase partition/native request join and load-timeout-stage tests; injectable-clock Runner tests |
| Keep native runtime and process evidence separate | BatchRunner captures actual backend/revision, worker PSS, runtime/admission/allocation snapshot, artifact/plan identity and worker/session/measurement lease before cleanup. Native phase observations carry operation/request IDs. Configured offload/thread values are separately named. | Measurement runtime identity test; Cleanup test; export unknown-identity test |
| Preserve unknown throughput for one buffered chunk | Reference delivery requires multiple chunks, a positive interval, sufficient output and a successful comparable task. Buffered first-answer latency may still be available; native segment metrics remain separate. | Runner buffered-response test; timing eligibility and minimum-band tests |
| Unknown accuracy differs from a measured zero | `BenchmarkMetrics.kt` defines answer correctness, delivery completion, profile availability, planned success, timing and reasoning populations with denominators, exclusions and source IDs. Infrastructure outcomes are excluded from answer grading. | Queue policy unknown/zero/blocked tests; DynamicScoreEngine infrastructure tests |
| Keep prior capability visible alongside latest availability | `DynamicScoreEngine` retains eligible complete capability blocks and separately uses applicable recent attempts for availability/latest status. Overall remains unknown with a missing mandatory capability or timing band. | DynamicScoreEngine completeness, newer blocked attempt and unsupported-tool tests |
| Repeated reasoning fixtures are not extra independent questions | Each run is graded first, then comparable complete run scores aggregate by median with range, run count and unique fixture coverage. Semantic correctness and JSON format remain separate. | IntelligenceBenchmark tests and DynamicScoreEngine reasoning aggregation tests |
| Distinct execution identities and compatible comparisons | Result IDs and comparison cohorts include effective configuration, versions, actual backend/accelerator/runtime, context, capability and load/cache declarations. CPU and GPU results remain distinct; incompatible deltas are suppressed. | Comparison/retest tests; DynamicScoreEngine cohort tests; scoreboard identity tests |
| Suite 8 without silently rewriting suite 7 | Full remains 50 cases: 18 speed, 10 task, 6 JSON, 10 fixture-tool and 6 reasoning batches. Quick retains five logical cases. `BenchmarkSuite7.kt` and exact version lookup preserve the old manifest; unknown future versions stay ungradable. | Queue policy suite-diversity/frozen-version checks; Runner suite replay; Kotlin/Python scoreboard manifests |
| Compact export with honest state, defaults and evidence | `BenchmarkExport.kt` v2 keeps authoritative runs/attempts, explicit defaults, current metric provenance, phase/source evidence and safe frozen configuration. Diagnostic export adds events/history. Active exports say `IN_PROGRESS_AT_EXPORT`; credentials and sensitive URL components are removed. | Export active-queue privacy, canonical defaults/unknown identity, compact/detailed and truncation regressions; legacy backup round trips |
| Reviewable UI with automatic failure continuation | `ProfileBenchmarkScreen`, `BenchmarkQueueCard`, `BenchmarkResultCard` and ViewModel provide Queue/Results/History, ordered selection, inline failures, details, Skip/Stop/Resume/Retry, actual backend and metric provenance. Scoring/comparison work is off the UI thread; displayed lists use lazy composition. | Production wiring plus host policy tests; device accessibility, responsiveness and screenshot review remain required |

Public submissions preserve a privacy-safe, versioned manifest and reject new-suite infrastructure failures as grading evidence. Kotlin and `scripts/scoreboard.py` share manifest/identity rules and test fixtures. The public ranking is separately labeled from the device-relative app rating. `python3 -m unittest discover -s scripts/tests -p test_scoreboard.py` passed all 15 tests on 24 October 2026. The Kotlin cross-surface regressions also passed in the completed [integrated validation](Stability_Implementation_2026-10-24.md).

## Existing native protections preserved

The GGUF code already performs CPU-only initial registration, staged load deadlines, bounded worker cancellation, quarantine and fresh-worker CPU fallback when the prior worker is confirmed stopped. Auto selection defaults to CPU unless the exact GPU setup has qualified evidence. Requested GPU qualification remains `NOT_TESTED` after CPU fallback. The benchmark work does not remove memory reserves, clear quarantine, infer GPU execution from a preference, or treat a cancellation receipt as engine readiness.

Evidence is in `GgufRuntimeAdapter`, `ProcessLocalRuntime`, `LocalInferenceService`, `PlannedLocalRuntime`, the GGUF JNI/CMake backend initialization, and the existing `GgufInitializationRecoveryTest`/runtime admission tests.

## Explicit unknowns and practical limits

- Current worker interfaces expose worker generation and conversation identity. They do **not** expose a reliable engine-instance ID, driver revision or actual offloaded-layer count. Exports retain null plus `unknownFields` for these values; configured layer/thread values cannot fill the missing actual observations.
- A physical request ID establishes an admitted generation attempt. It is not proof that HTTP bytes reached a provider. Interrupted attempts can remain dispatch-uncertain and are not silently replayed.
- Client PSS, worker PSS and native allocation observations describe different scopes and sample times. Missing worker/native observations remain unknown.
- Phase intervals are client-observed elapsed intervals. Native segment counters have their own scope. Unreported setup/cache reuse or request controls are not inferred from a prior successful run.
- Quick is a small, provisional fixed-fixture screen. Repetition increases run count, not unique question count. Deterministic fixture checks do not establish general intelligence or semantic truth.
