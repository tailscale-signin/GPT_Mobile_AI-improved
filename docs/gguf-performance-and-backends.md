# GGUF prompt cost and device qualification

Local request planning now selects relevant capabilities before allocating context. A greeting without attachments or custom tool instructions has no schemas or tool boilerplate; ordinary writing omits unrelated tools. Explicit tool requests, including “Hi, search the web…”, retain their required capabilities. Tool-dependent tasks retain a small relevant set and authorized discovery. Stable system instructions no longer start with a changing clock. The native model still generates the answer.

GGUF metadata inspection uses buffered reads, bounds every skip, skips fixed-width arrays in one operation, and skips vocabulary strings without decoding them. Compact metadata and verified checksum receipts survive worker restarts in app-private storage. Receipt keys require inode, nanosecond change time, size and modification time; Android uses `Os.stat` when NIO lacks a Unix attribute view. Changed or unverifiable files undergo full validation. Concurrent checksum work shares a file lock.

The normal Android build packages CPU, Vulkan and OpenCL. OpenCL uses pinned Khronos headers and a hidden static ICD dispatcher that opens the device's optional `libOpenCL.so`; it does not replace the vendor library. ARM64 builds enable upstream runtime-selected KleidiAI kernels. Cross-compilation retains `GGML_NATIVE=OFF` and optimized Debug flags. Build flags `ggufVulkan=false` and `ggufOpencl=false` can omit the optional backends.

GGUF profiles offer CPU, Vulkan GPU, OpenCL GPU and Auto. Explicit GPU starts with eight offloaded layers. The device comparison screen measures progressively larger offload only after a successful smaller configuration. Auto chooses a configuration with retained successful generation and actual device-layer evidence for the same model, runtime/app build, firmware, driver, context and batch; otherwise it uses CPU. CPU Auto keeps its conservative default until repeated benchmark measurements support separate prefill/decode thread choices. A two-token greeting cannot qualify CPU tuning. The prefill governor adjusts effective batch from measured tokens/time toward a 2.5-second cancellation window.

The existing native exact-prefix cache remains in use. Final native metrics now export processed and reused prompt tokens plus prefill/decode durations even when verbose logging is off. Phase progress includes effective batch, processed/total prompt counts and the actual backend. Durable bounded runtime incidents retain inspection/load measurements, backend/device/driver/layer receipts, original caught errors, CPU fallback, and process disconnections. A bounded last native error survives a worker exit. Both conversation and settings log exports include these records. No prompt or answer text is added to incident history.

Caught GPU failures carry typed categories and preserve the original native message. CPU recovery occurs only after cleanup and before visible output; Combined single-pass requests disable generation recovery. Native process crashes remain quarantined until explicit verification or backend selection. Packaging or a successful load alone is not GPU qualification.

## Validation

Host JNI smoke exercises real CPU inference, both chat-template formats, prefix reuse, cancellation, context limits and repeated sessions. Android ARM64 native builds cover OpenCL, Vulkan and KleidiAI compilation. Kotlin regression tests cover prompt selection, metadata bounds/cache invalidation, durable digest receipts, typed errors and measured plan selection.

Before claiming a performance improvement on a phone, measure a cold greeting and immediate follow-up with the exact Gemma artifact, then compare longer prefill/decode workloads. Run the Vulkan and OpenCL instrumented generation checks on the device and retain actual offloaded-layer and driver receipts. No desktop build or unit test establishes Snapdragon throughput, thermal behavior, kernel dispatch or model/driver compatibility.
